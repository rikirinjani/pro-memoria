# V0.5 Context Scaling & Token Economics — Pre-Experiment Report

## 1. Research Question

> Does bounded PM-1 state transfer scale more efficiently than repeatedly
> transmitting accumulated conversational context as task horizon increases?

V0.4a established that PM-1 preserves semantic state across 100 sequential
handoffs (100% state integrity, 100% digest continuity, zero drift, zero
protocol-induced failures). V0.5 is a **token/context scaling** study, not
another endurance test: it measures how the transmitted context grows with
horizon under two handoff strategies.

## 2. Hypotheses

- **H1 — PM-1 cumulative transmission is ~O(N):** the PM-1 packet is bounded
  per handoff, so cumulative transmitted context grows approximately linearly
  with horizon N.
- **H2 — Conversational cumulative transmission is ~O(N²):** the accumulated
  transcript grows linearly with hop, and cumulative transmission sums a
  growing series, giving approximately quadratic growth in N.
- **H3 — PM-1 becomes relatively cheaper as horizon grows:** C/P cumulative-token
  ratio increases with horizon; percentage reduction 1−P/C grows.
- **H4 — Reliability equivalence:** both conditions solve the same task with
  comparable correctness at equal horizons (no fairness violation).
- **H5 — Context ceiling:** conversational context approaches the model window
  at some horizon while PM-1 stays bounded.

H1–H3 and H5 are hypotheses to be **tested against measured data**, not
assumed. The benchmark is capable of producing PM-1 advantage, no meaningful
difference, or conversational advantage.

## 3. Experimental Design

Two handoff strategies operate on the SAME deterministic task:

```
Condition P (PM-1 state handoff):      worker -> PM-1 state -> next worker
Condition C (conversational handoff):  worker -> accumulated history -> next worker
```

Both execute identical initial state, target schedule, scenario, model,
temperature, max output tokens, handoff count, oracle, and success criteria.
The only independent variable is how state/history is transmitted.

## 4. PM-1 Condition Definition (P)

At every handoff the worker receives only the current PM-1 state packet
(sections->records->payload with position_qty, target_signal, cash_cents,
instrument, price_cents, logical_tick, tags) plus the immutable task
specification. The packet is bounded with respect to historical horizon —
same shape at hop 1 and hop 1000.

## 5. Conversational Condition Definition (C)

At every handoff the worker receives the accumulated chronological transcript
of prior (state -> action) entries plus a current-state line, plus the same
immutable task specification. The transcript is NOT truncated: it grows with
every hop. Each entry is naturally occurring conversation content
(`step k: state(position_qty=..., target_signal=...) -> action BUY (quantity 1) | reasoning`).

## 6. Fairness / Equivalence Controls

- Identical initial state, target schedule, scenario, model, temperature,
  max tokens, handoff count, oracle, success criteria (test-verified).
- Condition C receives only information that would naturally exist in an agent
  conversation: prior state/action pairs + current state. No benchmark
  metadata (horizon, trial, scenario, seed, expected action, oracle output,
  token counts, condition name).
- Condition P receives only its state boundary: the current PM-1 packet.
- Neither condition receives information unavailable to the other about the
  task itself (both can determine the current state and the required action).

## 7. Horizon Matrix

10, 25, 50, 100, 250, 500, 1000 hops.

Generated prefix-consistently: a master 1000-hop spec per chain is truncated
to each horizon, so every horizon evaluates a prefix of the same task.
Additional horizons can be added without changing the architecture.

## 8. Scenario Design

Reuses the V0.4a deterministic chain pool (10 chains, base_seed=42) covering
HOLD/BUY/SELL-producing states, zero/positive/negative positions,
multi-unit differences, and target changes. V0.5 uses initial state + target
schedule only (no corruption — corruption belongs to V0.4a).

## 9. Model Configuration

- Model: deepseek-v4-flash (same as V0.4a; no documented reason to change)
- Temperature: 0.0
- Max tokens: 2048
- Endpoint: https://api.deepseek.com/v1 (from `.llm_creds.json`)
- Identical between P and C. No heterogeneous models in V0.5.

## 10. Token Measurement Methodology

- Real provider `usage` block (prompt_tokens / completion_tokens) captured per
  hop by `LLMV05Worker.last_usage`; recorded as input/output/total per hop.
- Cumulative input/output/total tracked per hop and per chain.
- When the provider omits usage, `usage_available=False` and a deterministic
  chars/4 estimate is used — reported explicitly, never silently zero.
- Economic: model/provider/config recorded; cost left parameterized (no
  hard-coded price).

## 11. Context Measurement Methodology

- Transmitted context size per hop: characters (exact) and estimated tokens
  (chars/4). This is the deterministic ground truth for scaling.
- Max transmitted context per chain; cumulative transmitted context.
- PM-1 packet size (chars) recorded per P hop; conversation history size
  (chars) recorded per C hop.

## 12. Scaling-Analysis Methodology

- Fit linear and quadratic least-squares models (pure-python normal
  equations) to cumulative tokens vs horizon for P and C separately.
- Report coefficients, R² for both fits, observed growth ratios
  (cum(H)/cum(H/2)), and tokens/handoff at each horizon.
- Relative efficiency per horizon: `Cumulative(C)/Cumulative(P)` and
  `1 - P/C`.
- Conclusion is based on measured data. No artificial quadratic curve is
  manufactured; if the conversational implementation naturally reuses compact
  context, that is documented honestly.

## 13. Reliability Metrics

Per condition/horizon: action correctness (vs received state), received-state
correctness, oracle-state correctness, state integrity (divergence==0), digest
continuity, semantic drift (max/cumulative |divergence|), handoff survival,
chain survival, parse errors, worker failures, failure taxonomy counts.

## 14. Acceptance Criteria (registered before API calls)

| Criterion | Threshold |
|---|---|
| Reliability equivalence P vs C | handoff success within ±5 pp at each horizon |
| P cumulative-context scaling | linear R² ≥ 0.95 on cumulative transmitted tokens |
| C cumulative-context scaling | super-linear: quadratic R² > linear R² on cumulative transmitted tokens |
| PM-1 boundedness | P max transmitted tokens grows ≤ 2x from h=10 to h=1000 |
| C context growth | C max transmitted tokens grows > 5x from h=10 to h=1000 |
| Zero metadata leakage | all prompt-isolation tests pass |
| Zero oracle leakage | workers do not import oracle |
| Deterministic reproducibility | identical config -> identical expectations |
| Token completeness | token_usage_available recorded on every hop (or explicitly marked unavailable) |

## 19. Threats to Validity

- Token estimates (chars/4) used offline may differ from provider tokenization;
  real runs use provider usage when available.
- Conversational transcripts are a constructed, stylized conversation; a real
  agent's accumulated context could differ in format and growth.
- The model context window (default 65,536) must be set to the provider's
  actual window; a wrong value changes the ceiling interpretation.
- A single model (deepseek-v4-flash) and one task family limit generalization.
- C's transcript contains prior reasoning, which P omits; this is inherent to
  the two mechanisms and documented (both still determine the same action).
- No statistical significance claims for small trial counts; scaling
  conclusions come from the fit quality across seven horizons.
