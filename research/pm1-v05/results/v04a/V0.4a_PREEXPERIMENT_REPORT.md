# PM1 Trading Benchmark v0.4a — Pre-Experiment Report

100-Hop PM-1 Sequential Handoff Benchmark

## Research Question

Can PM-1 preserve correct semantic state across 100 sequential agent
handoffs without state loss, corruption, or semantic drift?

The benchmark tests the protocol/state transition itself across independent
worker contexts — not single-prompt policy execution (that was V0.3a).

## Benchmark Architecture

```
Initial State
    ↓
Worker 1  →  PM-1 handoff  →  Worker 2  →  ...  →  Worker 100
    ↓
Final State
```

- 10 independent chains × 100 sequential handoffs = 1,000 handoffs per
  condition.
- Each worker runs from a fresh context (new messages array every hop).
- The only state transferred is the PM-1 handoff representation plus the
  immutable task specification.
- The oracle validates every hop independently against hidden ground truth.

## Handoff Semantics

At every hop:

1. **Input** — worker receives the current state representation (PM-1
   packet for H-full/H-corrupt/H-recover; plain text for H-direct) plus
   the immutable task specification.
2. **Processing** — worker decodes the state, determines the required
   action, applies it, produces the next state, emits the next handoff.
3. **Output** — the next worker receives only the emitted state.
4. **Validation** — the oracle independently computes the expected action
   and expected next state from hidden ground truth and compares.

**State semantics:**
- Oracle trajectory = `compute_expected_action(position, target)` applied
  deterministically every hop.
- Actual trajectory = what the worker emits (`next_position_qty`), carried
  into the next hop.
- Divergence at hop h = `actual_position[h] - expected_position[h]`.
- Worker correctness is judged **fairly**: against the policy applied to the
  state the worker actually received (which may be corrupted). Injected
  corruption is therefore never mislabeled as a worker failure.

## Chain-Generation Methodology

- Deterministic generator (no uncontrolled randomness): `generate_chain_specs(base_seed=42)`.
- Each chain: `chain_id`, `generator_seed`, `initial_state`, `target_schedule`
  (100 per-hop targets), `corrupt_hops`, `restore_hops`, `scenario_metadata`.
- Chain seeds derived via SHA-256 of `v04a:{base_seed}:{index}`.
- Target schedule changes at deterministic boundaries (every ~33 hops) so a
  chain never converges to a trivial fixed-point HOLD.

## Conditions

| Condition | Description | Corrupt hops | Restore hops |
|---|---|---|---|
| **H-full** | Normal PM-1 handoff (packet) | — | — |
| **H-direct** | Control: equivalent plain-text state | — | — |
| **H-corrupt** | Controlled corruption at seed-driven hops | yes | — |
| **H-recover** | Corruption then oracle-state restoration | yes | yes (hop+1) |

Corruption injection: `received_position = actual_position + 1` at the
seed-driven corrupt hops. Restoration: received state is replaced by the
oracle state at the following hop.

## Oracle Methodology

- `lib/oracle.compute_expected_action` — unchanged, independent, hidden.
- Expected trajectory computed from hidden ground truth only.
- Worker modules never import `lib.oracle` (test-verified).
- Per-hop record: `expected_state`, `actual_state`, `expected_action`,
  `actual_action`, `state_digest`, `behavior_digest`.

## Anti-Leakage Controls

Every hop's prompt contains only:
- the state representation (PM-1 packet or plain text), and
- the immutable task specification.

Test-verified absent from prompts: chain ID, hop number, generator seed,
expected state, expected action, oracle output, condition name, previous
worker reasoning, previous conversation history.

Fresh-context verification: consecutive hops construct brand-new message
arrays; no mutable prompt object is reused; each hop is a single LLM call.

## Failure Taxonomy

| Classification | Meaning |
|---|---|
| PASS | Worker correct given received state |
| STATE_LOSS | Worker produced no next state (missing position) |
| STATE_CORRUPTION | Correct action but wrong emitted next state |
| ACTION_ERROR | Worker action differs from policy on received state |
| PARSE_ERROR | LLM output unparseable |
| INVALID_STATE | Emitted position outside sanity bound (±50) |
| HANDOFF_ERROR | Representation encode/decode machinery failure |
| RECOVERY_FAILURE | H-recover chain never re-joined oracle trajectory |
| INCONCLUSIVE | Reserved for ambiguous machinery cases |

## Metrics

- Handoff Success Rate = successful handoffs / total handoffs
- Chain Survival Rate = chains reaching hop 100 with zero semantic state loss
- First Failure Hop (per chain)
- State Integrity = fraction of hops with divergence == 0
- Action Accuracy (vs oracle action on true state; and vs policy on
  received state)
- Semantic Drift = divergence series, max |divergence|, cumulative |divergence|,
  mean |divergence|
- Recovery Rate (H-recover) = chains returning to oracle trajectory /
  chains subjected to corruption
- Token Cost = input, output, cumulative, average per handoff
- Digest Continuity = fraction of hops where actual state digest == expected
  state digest (digest over semantic fields only, independent of chain/hop/
  trial/run ID)

## Hypotheses

- **H1 — PM-1 continuity:** H-full maintains semantic state correctly across
  100 hops.
- **H2 — Direct-state equivalence:** H-full performs comparably to H-direct
  (PM-1 adds no semantic degradation).
- **H3 — Long-horizon stability:** semantic error does not systematically
  increase with hop number (trend in {zero, constant}, not
  gradually-increasing/catastrophic).
- **H4 — Corruption sensitivity:** H-corrupt changes the state/action
  trajectory when corrupted state is trusted (propagation observed).
- **H5 — Recovery:** H-recover returns to the oracle trajectory after correct
  state restoration.
- **H6 — Deterministic reproducibility:** identical initial state + identical
  transition sequence produces identical benchmark expectations.

## Acceptance Criteria (pre-registered, before any results)

| Criterion | Threshold |
|---|---|
| H-full 100-hop chain survival rate | ≥ 70% |
| H-full handoff success rate | ≥ 95% |
| H-full state integrity (divergence==0) | ≥ 95% |
| H-full vs H-direct equivalence | survival within ±5 percentage points |
| Long-horizon drift | trend ≠ gradually_increasing, ≠ catastrophic_after_threshold |
| Corruption propagation (H-corrupt) | ≥ 1 corrupt hop shows divergence ≠ 0 in ≥ 90% of chains |
| Recovery rate (H-recover) | ≥ 70% of corrupted chains recover |
| Zero metadata leakage | all anti-leakage tests pass |
| Zero oracle leakage | worker modules do not import oracle |
| Reproducibility | identical config → identical expectations |

These thresholds were fixed before the pilot or full experiment ran.

## Known Limitations

- Corruption is a deterministic +1 flip; more complex corruption (target
  changes, negative flips) is possible future work.
- The LLM worker must emit `next_position_qty` — this is a new contract not
  exercised in V0.1–V0.3a.
- Token accounting depends on provider `usage` block; offline/deterministic
  runs record zero tokens.
- Chain survival for H-corrupt is expected < 1 by design (injected
  divergence); survival is the primary criterion for H-full/H-direct.
